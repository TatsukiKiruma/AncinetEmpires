# 真实 APK 对局与当前规则核验报告

本次仅核验和报告，未修改项目规则、回放导入器或交付压缩包。结论：当前项目不能认定已完整对齐全部真实回放。既有已确认 mod、尚未归因的状态分歧，也有能够独立复现的项目导入与回合结算问题。

## 数据来源与范围

- 7 月抓包：125 份原始 game_get 响应，按原始字节 SHA256 去重为 112 份。
- 9 月服务器下载：145 份，逐份与 download_report.json 的 SHA256 匹配。
- 合计 257 份唯一响应、301844 条动作记录；全部可解密、解析，顶层与动作数组未消费字节均为 0。没有使用旧模拟器生成的 2000 多局。
- “不到 100 局”对应历史清洗清单中的 78 局完整候选，原始文件 SHA256 全部匹配。它是 112 份中的子集，不是全部真实数据；历史“完整”标签包含旧引擎结论。
- 场景标识：SD 252、SO 3、SR 2。响应可能只包含对局前缀，读取所有记录不等于包含整场对局。

## 已定位的项目问题

1. **开局 HP 导入固定为 100。** tools/apk_game_get_validate.ts 的 createUnits 没有按等级和生命成长赋值。APK C0600q.m4333c 明确用 baseMaxHp + maxHpGrowth × level 创建单位。e964 的 4 级石人应为 200 HP，当前却为 100，过早死亡造成 record 35 找不到目标。独立诊断只校正初始 HP 后，全 60 条严格无损通过。
2. **投降前缀导致初始玩家推断错误。** inferInitialCurrentPlayer 计入前导 NEXT_TURN，却没有正确处理此前 SURRENDER 造成的换人。656 的当前初始玩家为 P1，record 2 轮到 P3 却要求 P2 单位行动。诊断改为 P0 后，全 3547 条严格无损通过。
3. **淘汰后的自动换人缺少回合开始结算。** engine.ts 的 ensureCurrentPlayerCanAct 只更改 currentPlayer。40c 在第 15 回合 P4 淘汰后转到 P5，其单位仍 hasActed=true，record 881 被拒绝。独立诊断补执行 P5 回合开始后，全 1114 条严格无损通过。该实验在 dfe 上无切换发生，仍于 record 4121 失败，不能用同一原因解释所有样本。
4. **SO 错误地禁止指挥官重招募。** 041 的场景标识是 SO，record 180 招募 ID 9 指挥官。SO/controller.js 将普通招募列表设为 0..8，但 APK C0600q.m4302g 用 OR 独立允许存在阵亡储备的指挥官；C0789f0.mo3077m 也在普通列表之外将指挥官插入招募 UI。当前 apk_skirmish.ts 将 SO 指挥官费用设为 null，招募列表又不含指挥官，遗漏了这条特殊路径。诊断保留 SO 普通兵种限制，仅恢复指挥官分支后，660/660 严格无损通过且胜者为 2。默认 SD 验证掩盖了该问题，故不能只用默认模式的通过数验收 SO。

上述诊断都是临时脚本中的归因实验；没有应用到项目源码，也没有把实验通过计入当前版本验收结果。

## 动作通过仍可能存在的状态错误

HP 导入差异覆盖 5 份、38 个开局单位；其中部分动作序列可以通过，说明合法动作兼容无法替代逐状态比较：

| game_get_e9648915cc5f975129d3a4d3.bin | 15 |
| game_get_20260704_131516_044.bin | 9 |
| game_get_20260704_132153_085.bin | 4 |
| game_get_20260704_132710_112.bin | 2 |

257 份已核对的单位战斗、移动、经济、能力字段，以及地形类别、通行、回复、破坏与修复字段，均与 APK 静态表一致。内嵌规则参数仅等级上限有差异，属于正常设置，不能当作 mod 证据。运行时脚本、移动覆盖和临时状态仍可能不在这些静态表中。

对 6efeed，项目在 record 7822 看到目标龙为 140/100 HP，因而不生成治疗动作；APK C0600q.m4295h 同样要求 HP 不高于上限。目前不能把“取消治疗上限检查”作为修复结论。dfe 的 record 4121 目标格仍有 P3 美人鱼 20 HP；097 的占位分歧同样需要前序伤害、死亡和脚本状态的独立证据。

## 对训练的影响

当前不应把上述异常样本的模拟器状态、动作 mask 或终局标签直接当作 APK 真值。已确认 mod 应单独分组；疑似项保持待定，不与标准规则样本混标。通过的动作序列只能说明在这条路径上兼容，尚不能证明每一步 HP、金币、经验、人口和自然胜负与 APK 相同。

本次没有 Android 实机逐步状态快照；所有结果均标记 apkStateCompared=false。完整校验结果、逐局分类及文件哈希见 [逐局 JSON](real-replay-audit-20261013/per-replay-results.json)、[逐局 CSV](real-replay-audit-20261013/per-replay-results.csv) 和 [汇总及源码身份](real-replay-audit-20261013/summary.json)。

## 复现方式

在仓库根目录执行，输出使用新路径以保留本次证据：

```powershell
npm run apk:game-get-validate -- --dir captures/mitm_replay --allow-ambiguous-recruit --out .tmp/recheck-july-strict.md
npm run apk:game-get-validate -- --dir captures/cloud --allow-ambiguous-recruit --out .tmp/recheck-september-strict.md
# 强制模式分别追加 --force-apk-replay-execution；SO 单文件另外传 --mode SO。
```

严格与强制报告全部为本次重新运行，未把历史报告当作当前通过结果。每份输入 SHA256、首个失败记录、诊断现场和信息损失计数均保留在证据目录；sourceHashes 固定了本次使用的规则源码版本。
