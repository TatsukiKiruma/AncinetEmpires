## 1. 好消息：状态本身基本不重复

```
rows                    : 30000
distinct spatialTensor  : 27991   (row/state = 1.07)
rows sharing a tensor   : 2009 (6.7%)
max multiplicity        : 6
distinct full rows      : 30000
```

在"状态去重"这个轴上，数据集是干净的：只有 6.7% 的行与另一行共享同一个张量。
所以 **F09 的问题不是行重复，而是行所归属的"局"太少（约 20 局）导致的轨迹相关性**。
这两件事必须分开说，不能混为一谈。

## 2. 需要登记的问题：43.3% 的状态其候选动作被截断在 48

```
candidateActions 宽度分布（节选）：
    3 -> 1084      10 -> 556      20 -> 501      30 -> 201      40 -> 142
    4 ->  816      12 -> 576      22 -> 419      32 -> 185      45 -> 109
    5 ->  730      15 -> 507      25 -> 314      35 -> 180      47 -> 114
    ...
   48 -> 12978      ← 43.3% 的行堆在截断上限
```

转换器用 `maxCandidatesPerState: 48`（`tools/convert_archive_to_spatial.ts:231`）。
**12,978 / 30,000（43.3%）的训练状态，其候选集合正好等于 48 —— 即被截断。**

后果：
- 对这些状态，真实合法动作集合比模型看到的大，模型学到的分布是"截断后的合法集合"上的分布。
- 这与 V11 在搜索侧花费大量精力修的 F03（根候选遗漏必要单步动作）是**同一类风险，出现在训练数据侧**：
  `v11/out/candidate_coverage.json` 用 8 个真实局面证明了搜索侧 `baselineAlwaysPresent = true`、
  `positionsWithMissingTypes = 0`，但**训练数据集本身没有做过等价的覆盖审计**。
- 转换器保留了 target action 与指挥官招募（`:128-133`），所以"标签动作仍在候选内"大概率成立；
  但**"基准首选/立即制胜/pending 解决动作是否仍在候选内"从未被验证**。

建议（并入 T12-03 的验收）：对转换后的数据集复用 `tools/v11` 的覆盖检查口径，
至少报告"基准动作在候选内的比例"与"被截断状态中动作类型缺失的比例"。
