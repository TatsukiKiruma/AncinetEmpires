# 招募拒绝、慢速与整队列停止的根因

2026-10-22。分析对象为指定困难 APK、实际下发的冻结手机采集源码、失败局原始文件及旧版真实计时。分析期间没有修改 APK、规则、采集器或启动新的训练对局，手机仍为完成2/1000、队列停止。

## 结论

1. 招募龙失败存在明确规则错配：原生人口上限30，困难网页代码固定100。原生最后保存状态人口26，龙权重5；网页接受31≤100，原生拒绝31>30。
2. 原 APK 本来允许从JS失败转入Java困难策略继续决策。采集器主动禁止该路径，又把单局失败升级为全队列退出。这两项是工程选择，不是用户要求或游戏必须如此。
3. 旧版几秒一局有真实证据。新运行901个成功动作耗时1152.792秒；约78.3%在网页响应窗口之外，不能把整段耗时归给困难JS搜索。
4. 高频Frida观察、每事件flush/sync、全应用Java去优化、Java/JSON/WebView往返，构成明显不同的执行条件。熄屏后还出现约2.59倍周期放大。尚无控制变量对照，不能把各因素的因果占比或优化收益编造成精确数字。

## APK与现场身份

`TARGET_IDENTITY_CONFIRMED.json`记录目标APK SHA为`a2adcc856384dea4ebac7434c78c2abbdcb1f428e502925fd4beb39c95cd6d48`，HTML SHA为`6076f354362f89c0a0abbcb10ef4de04d321f96aa7de90e61f0fb33a2ea883eb`。静态HTML与APK内资产逐字节相等；另从目标APK本身提取`q.b(III)Z`的49条指令，确认实际方法读取金钱l、已用人口t、上限m并执行相加比较，不只依赖旧版JADX文件。

失败尝试`hts1000-20261022-0003-a02`的六件已有原始文件完整保全在`failed-native/`，SHA见`RAW_SHA256.json`。没有final/result是因为本局没有自然完成，不能把901步伪装成完整父局。

## 为什么招募被拒绝

失败请求是第902次动作尝试（索引901），蓝方第69个阵营回合，JS返回`recruit,row=4,col=13,unitType=8,unitId=dragon`。回调正常到达，`createAction`返回null，没有桥超时。

从901帧原始状态流提取最后一帧，即动作900前态；`inspect_snapshot.ts`通过既有原生解码器读取，未重新编写游戏规则。`snapshot-900-inspection.json`显示：

| 原生项目 | 值 |
|---|---:|
| 当前玩家 | 0（蓝方） |
| 金钱 | 1050 |
| 龙的价格 | 1000 |
| 本队人口上限 | 30 |
| 本队人口 | 26 |
| 龙人口权重 | 5 |
| 目标格单位 | 空 |
| 待部署单位 | 无 |

随后唯一已提交动作900是单位从(11,13)移动到(11,11)并待机，未招募、结束回合或改变人口/金钱。原生人口计数按单位定义权重相加，包含待部署单位；现场无待部署单位。`C0600q.m4298h`第1091行以后及`m4259s/m4285j`确认该计数公式。

`ResourcePackHardAi.createAction`在招募分支取unitType/col/row，调用原生`q.b(8,13,4)`。目标方法确认费用和人口条件；`26+5<=30`为假，返回false，桥因此返回null。dragon到8的映射正确，金钱也足够。

困难网页`hard-ai-runtime.html:7518`却写死`TEAM_POPULATION_LIMIT=100`，第7538行使用这个常量做相同相加判断。网页正确按人口权重计数，龙也占5；错误是上限来源。Java桥的`createSnapshot`没有把原生`f.m`传入teams，网页适配层也没有读取每队真实上限，因此在31人口时仍认为可招募。

静态源码位置：

- `deliverables/original_apk_hard_20261021/static/patch-ResourcePackHardAi.dad.java:190`，招募转原生合法性检查。
- 同文件第538–587行，队伍快照字段没有人口上限。
- `APK/_analysis/jadx_output/java/p036c/p037a/p039b/p040a/C0600q.java:698`，原生完整招募条件，人口表达式位于705行。
- `deliverables/original_apk_hard_20261021/static/hard-ai-runtime.html:7425`，人口累计；第7518、7538行，固定100与招募检查。
- `target-native-recruit-bytecode.txt`，本次直接从目标APK提取的实际字节码。

正确修复方向是将实际人口上限和必要招募条件传给网页，并让网页使用权威规则；保持原生规则与数据身份可追踪。不能把本次桥接缺口描述成龙兵种本身不受支持。

## 为什么整批停止

`patch-b.dad.java:1417`显示，`j.b.call()`先调用Hard.choose，若无有效动作，会继续执行Java困难逻辑。这仍属于困难档自身，不能混称普通AI。

本次冻结`resident_standalone.frida.js`在choose返回null时主动抛异常，在Java fallback入口也主动阻断。`controller.sh`收到failed后调用fail并exit，导致后997个尚未启动的父局一起停下。这是为了限定纯JS轨迹而采用的工程策略；它比“忠实采集APK困难档并标明各路径”更严格，原始用户附件没有明文要求这几项行为。

保留失败局、不计作完成是正确的；单次拒绝就永久结束1000局队列并非必然。可将失败隔离，在安全收尾后有界重试或继续其他父局；若保留Java困难回退，应逐动作标记并分别统计，不能冒称全部来自JS主路径。

## 为什么这么慢

详细历史口径见`CONTRACT_COMPARISON.md`。旧1000局全部中位3.970秒、均值7.791秒；筛选同八张官方双人图默认完整开局后，64局全部自然结束，单局中位1.920秒、均值2.159秒。旧Icy Paths八局中位4.914秒，最大6.530秒。因此用户所说不到10秒一局有实测依据，不只是残局或截断造成。

旧worker使用原生普通AI `j.a`；新worker调用困难类`j.b`及网页策略，算法路径本来不同。旧批次还使用8个采集线程，新困难桥是共享静态单例、串行执行。这些会改变算法成本与批次吞吐，但不能把当前重型观察条件下的用时当成未干预Hard算法的固有速度。

`analyze_timings.py`读取9933个已保存事件，按手机单调时钟分解901个完整动作周期，结果保存在`TIMING_BREAKDOWN.json`：

| 阶段 | 总秒数 | 周期占比 |
|---|---:|---:|
| begin→choose，含快照/AI对象准备和观察 | 229.689 | 19.92% |
| choose→browser，含桥快照与JSON准备和观察 | 280.379 | 24.32% |
| browser→入队，含桥/UI任务准备和观察 | 220.149 | 19.10% |
| 入队→网页回调 | 250.200 | 21.70% |
| 回调、动作转换、原生结算、其他阶段 | 172.375 | 14.95% |
| 合计 | 1152.792 | 100% |

平均1.27946秒/动作，中位1.20455秒，p95为1.84011秒。网页响应窗口之外902.592秒，占78.30%。响应窗口本身还包含审计、调度和回调，因此它也不是纯JS计算时间。

已经确认的工程负担：

- 每个成功动作11条审计事件；每条执行write、flush及FileDescriptor.sync，约一万次强制同步调用。独立版已经禁用send，不能把现存慢速继续归因于向电脑逐条发送。
- 为观察被内联的方法，调用了`Java.deoptimizeEverything()`。Frida官方明确该接口让整个VM改为解释执行。因此引擎拷贝、序列化、反射、结算也被置于不同运行条件，并非只影响AI入口。参考 https://frida.re/docs/javascript-api/ 。
- 每步在Rhino、Java、Frida JS与WebView之间多次往返；旧版Java线程内的普通AI循环没有这条高频观察链。
- 熄屏前动作0–119均值0.53862秒，已确认熄屏后的192–900均值1.39437秒，约2.59倍。多段非JS耗时同时升高，与熄屏有明显时间关联；缺连续CPU频率和受控亮屏对照，不能精确声称降频占多少。

901个动作间的commit→next begin最大仅0.088秒，未出现至少1秒的资源暂停等待；最后状态44℃且shouldPause=false。停止的实际错误是招募拒绝。性能损失不能解释为每一步都在等待60秒响应超时，也不能全部归因于温控暂停。

现有日志无法分别量化全VM去优化、同步写盘、桥接、搜索和CPU调度的独立因果占比。必须在相同地图/初始态、固定采集设置下做低开销对照，才能承诺优化收益。此前用前两局外推1000局完成时间依据不足，应撤回。

## 后续修正顺序

1. 补齐权威人口上限与招募合法性字段，修复JS和原生规则错配。
2. 生产采集去掉全VM解释执行和逐事件同步，使用有界缓冲及局末完整落盘；保留动作、快照和来源身份。
3. 故障隔离与有界重试，分别报告纯JS、Java困难回退、错误、截断；不把错误计为完成，不让单局错误默默结束整批。
4. 用同图、同初态的受控基准分别测原生普通AI、低开销困难AI及采集附加成本，再给1000局预计时间。当前不能保证困难AI一定也能达到10秒一局。

本报告是已完成的分析，不表示上述修正已经实现或部署。
