# 普通AI与困难AI采集的契约和性能责任界限

本分析只读取PC现有源码、用户附件和采集证据，未访问手机、未修改采集器、未重跑对局。结论范围是“哪些要求来自用户，哪些开销和停止行为来自采集实现”，不把未做受控测量的因素写成已证明的耗时占比。当前独立规则重放和训练准入后置，不因本报告提升数据资格。

## 用户要求与工程选择

用户原始附件为 `C:/Users/SHIINA/.codex/attachments/9f672c92-3e58-4bc1-b331-a07199ed4990/已粘贴的文本.txt`。其中明确要求来源可追踪、困难对手主路径与回退分别报告、截断和错误不伪造胜负、保全历史、未验收数据不冒充合格训练数据。之后用户将本轮改为直接采集1000局、独立验收后置；不能再用旧的1/20局验收流程冒充最新要求。

| 当前行为 | 依据与责任界限 |
|---|---|
| 普通 `c.a.b.c.j.a` 不能冒称困难AI | 符合用户要求的真实来源区分；旧worker确实调用普通类，新困难类为 `j.b`。 |
| 禁止任何Java困难fallback，桥返回null便报错 | 采集器选择的“纯JS主路径”契约，并非附件明文要求。原APK的 `j.b.call()` 本来就允许JS失败后进入Java困难逻辑；Java困难fallback不能称为普通AI。 |
| 一个动作异常就结束整条1000局队列 | 工程上的故障隔离策略，不是附件要求。错误局应保留、不得算成功；但安全结束失败进程后是否重试或继续其他父局，是另一项可设计的调度规则。 |
| 每个审计事件都 `flush` 加 `FileDescriptor.sync()` | 我们新增的持久化强度，不是“保存原始证据”必然要求，更不是Hard算法本身的工作。一次动作会产生多个审计事件，因此同步次数可远多于动作数。 |
| `Java.deoptimizeEverything()` | 我们为保证观察钩子覆盖而选择的全应用VM处理，不来自用户要求，也不属于原APK困难策略。不能把带该设置的用时当作未干预APK速度。 |
| 同一进程只跑一个困难父局 | 有实际架构依据：静态WebView及HTML只有一组pending/回合缓存。旧普通AI的8线程不能直接搬过来，否则会串局。独立进程/设备并行是另一个方案。 |
| JS加载20秒、决策响应60秒上限 | 来源于目标APK桥实现；与上面几项工程开销应分开。原prompt的4秒预算针对新模型根搜索，不能套为手机原生困难桥的内部预算。 |

以上“未见用户明文要求”只指本次核对的附件及现有设计文件，不猜测未提供的其他会话授权。

关键设计证据是 `ai_training/pretrain_preflight_20261022/HARD_COLLECTOR_DESIGN.md`：第26行明确Java回退仍是困难类自身；第38行说明20/60秒桥等待；第54–60行解释单例隔离与超时后先处理当前进程；第114–118行要求三种路径分开，并建议设备内缓冲、局末或有界批次拉取。原设计还明确不能把逐条观察开销当作正式采集性能。第166行的“回退为零”是该静态方案的准入选择，不能倒推成用户原话。

`HARD_SAMPLING_PLAN.json` 的 `requestedBothSides="hard-js"`、gateSequence及 `HARD_SAMPLING_SEMANTICS.json` 是工程协议产物，能够说明我们实施了什么，不能作为用户曾明文要求“所有fallback均禁止”的证据。

## 真实旧数据并非每局都很长

从 `captures/phone-storage-1000-20261015/phone-storage-1000-20261015-summary.json` 的逐局原生 `elapsed_seconds` 重算，并用同目录 `manifest.json` 选择旧 `sd-normal`、相同八张官方双人图：

|---|---:|---:|---:|---:|---:|
| 旧普通AI全部 | 1000/979 | 1,449,050 | 3.970 | 7.791 | 124.738 |
| 旧普通AI八图默认局 | 64/64 | 30,465 | 1.920 | 2.159 | 6.530 |
| 其中Crossed swords | 8/8 | 3,171 | 1.943 | 1.930 | 2.372 |

这说明旧数据快不只因为包含预设残局：相同八图的默认完整自然对局也很快。不过种子、实际轨迹、调用策略和采集观察设置不同，仍不是控制变量相同的算法比较。

新 `runs/production-02/jobs/0001`、`0002` 的原生result分别记录：Crossed swords 373动作、189.395秒；Duel 146动作、68.696秒，均自然结束。其采集边界内约为508和471毫秒/动作；旧同地图8局聚合分别约4.87和4.19毫秒/动作。这个明显差距属于“算法、桥接、观察和调度设置合在一起”的实测结果，不能全归因于困难搜索，也不能据此直接声称fsync或deopt占了其中多少。

旧1000局报告中的1909.887秒是分批并行生成墙钟合计，不能除以1000就当作每局原生线程耗时。真实逐局耗时总和为7790.828秒。整轮含导出、核验、USB恢复约79.37分钟。旧 `storage_controller.py` 每批100局、8个采集线程、4个重放线程；新Hard是单进程串行，并且每局重新启动/挂钩/收尾。旧普通AI批次吞吐不能直接移用到新Hard。

旧全部1000局包含19类配置及预设，979自然结束、21截断；新冻结方案为8图官方默认开局，HTML `Math.random` 没有被cfg.seed或Java aiSeed播种。即使相同原生seed，重试也不保证同一JS轨迹，不能把不同attempt拼成一条可复现父局。

## 当前开销与停队列的位置

- 旧 `tools/phone_training/worker.rhino.js:60` 构造 `j.a`；动作日志逐行flush，但没有每个审计事件的强制sync，状态输出为缓冲流。`storage_controller.py:70`按8线程分配任务。
- 新 `tools/phone_training_hard/resident_collect.frida.js:26` 每个审计事件flush+sync；第102、138行拦截JS null及Java回退；第365行全VM deopt。`collect_1000.py:233` 将异常转为整个宿主队列 `stopped_on_failure`。
- 实际手机独立版的冻结副本 `standalone-02/resident_standalone.frida.js:29` 同样每事件flush+sync，第109、145行阻断fallback，第599行全VM deopt。`standalone-02/controller.sh` 的 `fail()` 写 `stopped_on_failure` 后直接exit，failed/stopped分支调用它。
- 独立版已经把 `send()` 变为空函数、evidence改为gzip；这减少宿主消息和空间，不代表已经移除了同步写盘或deopt。不能继续拿已关闭的逐条send当作该独立版的现存主要瓶颈。

第三局某次JS响应不可用与队列停止是两件事：前者需要具体错误/响应日志说明；后者是我们选择的调度后果。不能仅凭“触发fallback”判定原版困难AI崩溃，因为未经拦截的原 `j.b` 可能会继续走Java困难逻辑。

## 可行改进，尚未执行

1. 先明确采样产品：若目标是忠实运行APK困难档，保留原生Java困难fallback并逐动作标来源，统计混合比例；不能仍标全部 `hard_js_primary`。若目标确实是纯JS示范，保留失败attempt，但在安全结束其owned进程后做有界重试或跳过隔离父局，避免单个父局无限卡住整队列。所有重试选择偏差须披露。
2. 将审计日志同步改为有界批量/时间窗口和局末同步，保留闭环事件及崩溃时可识别的未完成尾段；发布完整result和manifest之前，关闭并同步所有关键流。不能只取消sync却继续宣称每个最近动作均已抗掉电持久化。
3. 做去全VM deopt的独立候选，先确认目标观察点仍有完整闭环；必要时仅处理相关观察点。需小范围受控计时才能确定收益，不能先保证“去掉就快多少”。不覆盖现有失败证据或冻结采集源码。
4. 把计时拆成原生快照、JS桥排队/响应、动作转换、原生结算、审计写入/flush/sync及局间启动收尾。计时记录本身使用有界缓冲，避免再次用高频同步审计测出高频同步审计的开销。
5. 同进程维持单消费者；只有实际建立独立WebView/静态状态隔离后才考虑跨进程并行。错误、截断、纯JS成功、含Java困难fallback成功各自计数，不能用继续调度掩盖错误，也不能把一错停全队列说成用户强制要求。
