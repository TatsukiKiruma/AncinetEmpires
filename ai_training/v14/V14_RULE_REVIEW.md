### 1.1 v3.1 并没有保留全部候选

扫描对象：`v13/out/v13_20260924_t13/T13-07/data_v3_b0_v31/pool_v31_subset.jsonl`。

SHA-256：`6f9fe51678434befc67415ed5df90d15dbcf4833f7d6c5d549ceb453c36f1f0a`，与该轮训练指标中的数据摘要一致。

| 项目 | 本轮实测 |
|---|---:|
| 状态数 | 3,181 |
| 各行声明的合法候选数之和 | 803,275 |
| 实际存储候选数之和 | 764,105 |
| 少存候选的状态 | 1,949 |
| 缺失候选出现次数 | 39,170 |
| 少存候选却标记 `truncated=false` 的状态 | 1,949 |
| 存储目标下标与目标动作码不一致 | 0 |
| 治疗候选 / 缺行动者坐标 | 2,960 / 2,645 |
| 支援候选 / 缺行动者坐标 | 8 / 8 |
| 招募候选出现次数 | 99 |
| 其中恰好是教师标签的次数 | 99 |

缺失数是相对归档声明的 `candidateCountLegal`，没有在本轮对全部 3,181 个状态重新构建引擎合法动作集。即便采用这一较弱检查，数据也已经不满足自身声明。

源码原因位于 `v13/tools/reencode_v31.ts:113` 和 `:313`：

1. 标签动作直接使用 `src.label.action`；其他动作调用私有 `decodeActionCode`。
2. 私有解码器不支持招募、修理、召唤、突击后移动、摧毁城镇等类型。
3. `capture` 错误要求动作码携带坐标。正式编码是 `capture:<unitId>`，占领目标是单位脚下格。
4. `heal`、`support` 被解码成 `unitId`；正式字段分别是 `healerId`、`supporterId`，导致行动者坐标丢失。
5. 解码失败后直接 `continue`，仍输出 `truncated: false`。

因此标签不只影响候选位置，还决定某些动作是否出现、是否带正确特征。例如训练中的招募动作几乎只作为正确答案出现；实战中各种可招募兵种同时竞争。治疗动作的标签与非标签甚至走出了不同的特征路径。这是直接可定位的训练—推理差异。它对实际败局的贡献大小仍需修复后的对照训练测量。

完整重编码报告自己已经记录过被跳过的候选：招募 87,572、突击后移动 6,562、摧毁城镇 3,848、修理 512、占领 81、召唤 60。这些是完整重编码阶段的计数，不能与上述子集计数相加。

### 1.2 “网络学会选下标 0”缺少依据

Python 的 `SpatialResNet.forward_action_logits` 与 TS 的 `SpatialResNetPredictor.predict` 都对每个动作使用相同的打分网络。没有候选下标嵌入，也没有“第 0 类”专用参数：

```text
score(s, a) = 共享打分网络(棋盘特征、动作坐标、动作语义、全局特征)
```

在动作集合、动作特征和目标动作保持不变时，仅重排候选并同步重映射目标，理论上只会重排 logits；交叉熵目标不变。浮点求和细节和最高分并列时的首项选择需要单独检查。

本轮使用 V13 v3.1 seed 42 的实际检查点，对前 8 个状态的候选完全反序，再按原动作位置对齐：**logit 最大差均为 0，所选动作均相同**。这只是 TS 前向的有限核验；完整 Python 梯度和跨语言检查仍列入任务。

因此，旧数据标签在下标 0 的比例不能单独证明位置作弊；“永远选下标 0”的准确率也不能当成共享动作打分器必然可实现的类别先验。确定有问题的是标签参与候选选择、候选集合不同、特征不同。v3.0→v3.1 还改变了训练行数、候选数、样本选取与更新次数，不是只改变顺序的单因素实验。

### 1.3 当前动作特征错误估计了反击

`src/game/ai/spatial_tensor_encoder.ts:313` 只要目标预计不死，就在原状态中调用反向 `calculateDamage`。真实引擎在 `src/game/engine.ts:568` 之后按以下顺序执行：扣除攻击伤害、施加状态、处理攻击者经验，再判断普通反击/反击风暴，使用更新后的状态计算反击。

本轮构造合法样例：投石车距离 3 攻击士兵。

| 读数 | 结果 |
|---|---:|
| 攻击是否在引擎合法动作中 | 是 |
| 编码器预计反击伤害 | 50 |
| 引擎执行后的攻击者失血 | 0 |
| 受击士兵剩余 HP | 45 |

这会给“安全远程攻击”等动作提供错误输入。训练和推理同时使用同一错误特征，并不意味着特征符合规则。修复应引入明确的特征版本并核对旧权重兼容性，不能悄悄改变旧模型所解释的输入。

### 1.4 张量相等没有证明状态重建正确

`reencode_v31.ts:76` 将 Observation 改造成 GameState，但存在需逐项处理的字段差异：

| Observation | 引擎实际需要的含义 |
|---|---|
| `unit.status` 是字符串或 null，时长在独立字段 | `UnitStatus` 对象，含 `type` 与时长 |
| 墓碑用 `x/y` | `grave.pos.x/pos.y` |
| `rules.priceOverrides` | `rules.prices` |
| 回合顺序、有效属性等派生字段 | 应从原始规则与单位状态计算、验证 |
| 部分规则未完整序列化，如堆叠招募配置/战役事件详情 | 从可信初始状态与动作回放恢复，或明确标记无法恢复 |

原重编码的 `status: u.status ?? null` 和 `graves: obs.graves ?? []` 没有完成这些转换。旧池与新池的空间张量相等，可能只是重复了相同的还原方式；编码又会丢失一些状态信息，所以相等不能反推出完整 GameState 相等。

V13 名为 `python_ts_parity.json` 的工件自己注明没有比较 Python/TS logits 和 value。旧池也是 TS 转换器输出，仅仅被 Python 读取。它证明的是一次有限的重编码张量一致性，不能升级成跨语言推理与完整规则状态的一致性。

## 2. 按实际规则重新解释“模型差”

### 2.1 一次决策不是一个回合

单位通常可以先移动再攻击；一个玩家的回合里有多个单位、招募 pending、治疗、支援与突击后移动。支援还可能恢复特定单位的行动能力。原子动作数、玩家切换次数和完整轮次数是不同量。

`BattleSearchAI.evaluateCandidate` 最多继续 3 个己方动作，而且主动排除了 `end_turn`。仍轮到自己时直接静态估值；只有确实换到别的玩家后才探测有限回应。因此它常常没有看到对手的实际威胁。改进任务应依据引擎真实的 `currentPlayer`、规则事件和预算记录展开深度。

### 2.2 指挥官阵亡、占城与终局不是同一件事

默认 `defeatOnNoUnitsAndNoCastles=true`，其余单项淘汰开关默认关闭；各地图/模式可以覆盖。指挥官可否重招、价格如何上涨、是否保留经验，也由配置决定。

终局赢家是联盟 ID，`winner=-1` 是规则平局。不能机械地把杀死指挥官、杀死最后一个单位、占领一个城堡统一标为获胜。必须在真实 `step` 后读取 `winner` 与玩家存活状态。

### 2.3 占领有价值，但“此刻存在 capture”不等于“下一步必须 capture”

占领会使用该单位的行动机会。可能存在必须先处理的即时威胁，也可能其他单位的动作与占领可交换顺序。实际经济收益在相应玩家回合开始结算；敌军站在己方城堡上还会在城堡拥有者回合开始受到伤害。搜到接触城堡的局面与搜到完成占领、跨过回合开始的局面，评价不能混淆。

有效测试应验证“存在可证明的即时获胜占领却没有选择”“在没有优先冲突的隔离局面中，离开机会窗口前错过必要占领”等具体性质。普通对局里的 capture 选择率只能作为行为统计。

### 2.4 多人局不能简化成所有敌人同时回应

`getTurnPlayerIds` 只保留存活且未禁用玩家，按 ID 排序；联盟关系决定敌我。下个行动者可能是盟友，某个敌人也可能已被淘汰。

当前编码将多个敌方聚合，当前搜索叶子还用单个变量保存遍历到的敌方指挥官信息。是否需要补“下个敌方行动者”“相对回合距离”“各玩家经济与军力”等特征，要通过保持其他条件相同的状态对验证。候选特征没有碰撞，并不证明不同棋盘状态没有被压缩成同样的策略输入。

### 2.5 单一动作准确率不能完整衡量回合质量

有些不同动作只是交换无关单位的执行次序；另一些差异会漏掉反击、招募或直接致命。应同时报告逐动作准确率、经过验证的等价动作命中率、按规则构造的错误率以及整局表现。不能把约 31% top-1 直接翻译成“其余 69% 都是坏棋”。

本轮子集里移动标签 2,427/3,181，结束回合标签为 0，支援标签为 0。子集构建偏向候选多的中段状态，可能放大持续移动等偏差。这是抽样风险；其具体实战影响需要重新分层采样的实验。

## 3. 搜索教师结论需要收紧

`tools/v7_heuristic_bounded_search.ts:117` 的 `evaluatePositionHeuristic` 是确定性函数。随机数出现在启发式动作排序和后续 rollout，可能改变走到哪个叶子。V13 的不变性工件在 204 次比较里没有测到 Q 变化，因此“随机叶子最大化已经被证明是败因”应撤回。

静态叶子存在其他明确的近似：兵力按 `hp/100` 计值、价格既参与资产值又随规则变化、目标距离采用曼哈顿距离、指挥官危险用近距离规则、多人指挥官信息被合并。这些都是待检验的偏差来源。应拆分预算、回合边界、叶子特征、随机排序做受控实验，不是先加大接管力度。

V13 战术探测器也不足以单独裁决教师资格：

- `tactical_core.ts` 把攻击对方最后一个单位视为 lethal，未检查是否打死、对方是否仍有城堡。
- 使用 `u.maxRange/u.move` 等字段推测威胁，但真实 `Unit` 不保证含这些派生字段，应使用 `getEffectiveStats` 和真实可达/攻击计算。
- extended suite 把“任意 move/attack/heal/support”作为救援成功，未核验威胁是否解除。
- pending 场景的正确动作常是处理已招募单位，而探测器把继续招募当成成功。
- 下个行动者检测没有完整遵循有效玩家与联盟规则。

所以旧教师**尚未获得可信的更强资格**，可以继续研究；不能依据这些探测器宣布搜索路线在原理上失败。离线教师允许比在线模型慢，只要预算可控、标签可靠。是否满足在线 1 秒预算是另一项部署资格。

## 5. 对上一轮建议的明确修改

1. **保留**小样本可拟合性检查、统一候选契约、独立对局评估与教师研究。
2. **前移**规则测试本身的正确性、动作编解码、状态恢复、反击语义、真正的 Python/TS 推理核验。
3. **撤回**“只修候选顺序就解决了根因”“数据现在已干净”“叶子本身随机”“所有 DAgger 必须等更强教师”等过强结论。
4. **区分目标**：启发式教师可以用于缩小学生与它的差距，并在学生访问状态上纠错；要声称超越它，则需要独立对战证据和额外改进信号。
5. **实际训练是必交付项**：前置硬检查通过后，执行干净的单教师基线与对应对战。搜索教师未合格不阻塞该基线，也不自动阻塞诊断性质的启发式 DAgger。
6. **先证明再扩容**：按验证损失、关键错误和对战结果决定增加更新、独立轨迹、规则特征或搜索预算。8 个 epoch 后曲线仍在变化，不能把当前分数当成训练能力的上限。

当前最可信的解释是：数据和规则特征仍有直接缺陷，抽样缺少关键阶段，训练还没有完成可靠的可拟合性与泛化定位，而搜索改善信号尚未通过合格评测。各因素对败局的相对贡献，由任务书中的受控实验回答。
